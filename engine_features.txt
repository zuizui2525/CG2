================================================================================
【ZuizuiEngine用】ルートシューティングゲーム開発 - カテゴリ別優先順位ロードマップ
================================================================================

このテキストは、ルートシューティングゲームを作るにあたって、
「1. ゲーム製作」「2. エンジンの機能追加」「3. リファクタリング」の3つのカテゴリごとに
どの順番で進めるべきかを優先度順（依存関係順）に整理したものです。

--------------------------------------------------------------------------------
【全体の進行順】ゲームの機能実装 ➡ 必要なエンジン機能追加 ➡ 必要に応じたリファクタ
--------------------------------------------------------------------------------

基本は「ゲームを動かす（③）」ことを最優先とし、動かすために「エンジン機能（①）」が
必要になったら追加します。コードの整理や「リファクタリング（②）」は、
プロトタイプが正常に1周遊べるようになるまで原則として行いません。

================================================================================
③【ゲームの製作】の進める順（優先度順）
================================================================================
ゲームプレイの核となるプロトタイプから順番に構築していきます。

[ ] 1. フェーズ1：マウス軌跡の記録と Line 描画
       - マウスをクリックしながら動かした軌跡の座標配列（std::vector<Vector3>）への保存。
       - 溜まった座標同士を LineObject で画面につなぎ、描いた線が残るようにする。
       - Rキーで軌跡をクリアしてやり直せる機能。

[ ] 2. フェーズ2：Catmull-Romによるルート曲線化と自機・カメラの自動移動
       - 記録した軌跡の点の間を補間して滑らかな曲線にし、その上をCube（自機）が自動前進。
       - カメラの座標と注視点（LookAt）を動く自機の背後・前方に同期。カーブ等での速度一定化。

[ ] 3. フェーズ3：照準UIとマウス操作による3D射撃（当たり判定）
       - 画面中央のレティクル（スプライト）表示と、マウス操作。
       - クリック時にカメラ位置から照準方向へ見えない線（レイ）を飛ばすレイキャスト発射。
       - 線分 vs 的（AABBボックス）の衝突判定と、連射・残弾数制限、リロード（Rキー）。

[ ] 4. フェーズ4：戦闘システムの拡張（敵の反撃と複数ウェーブ）
       - コース上の敵の待ち伏せ出現と体力（HP）システム。
       - 敵からプレイヤーへ弾（球体）を撃つ処理と、自機（AABB）の被弾判定、HP減少、画面赤フラッシュ。
       - 敵の弾を迎撃して相殺する処理。
       - 複数の敵のウェーブ管理（そのエリアの敵を全員倒すまでカメラの自動前進を一時停止）。

[ ] 5. フェーズ5：顔（頭部）親子配置とヘッドショット、ゲームループ完成
       - 敵の胴体Cubeの上に、行列乗算で連動する「頭部Cube」を配置。
       - 頭部へのヒット（顔命中）を検知し、クリティカルダメージとスコア（高得点）加算。
       - タイトル ➡ 線引き ➡ ゲーム本編 ➡ クリア/ゲームオーバー ➡ タイトル のループ接続。

[ ] 6. フェーズ6：演出強化と提出準備（プロトタイプ完成後）
       - BGM・SEの追加、敵撃破時のパーティクル演出。
       - 障害物（壁やビル代わりのCube）の配置、画面上のテキスト操作ガイド。
       - ReplaySystemによる難易度の最終調整。独立した .exe ファイルのビルド。


================================================================================
①【エンジンの追加要素】の進める順（優先度順）
================================================================================
上記ゲーム製作の各フェーズで必要になったタイミングで、エンジン側に数学・判定機能を追加します。

[ ] 1. スクリーン座標から3D空間へのレイキャスト生成機能
       - 目的：マウスのクリックしたスクリーン位置から、3D空間への投影（線を引くための座標特定）
               および照準から弾を飛ばす（3D空間のレイ生成）ための数学関数。

[ ] 2. Catmull-Rom 曲線補間計算ユーティリティ
       - 目的：手動で引いたカクカクの点配列から、滑らかな曲線座標の配列を自動生成する。

[ ] 3. 3D交差判定（線分 vs AABB、球 vs AABB）ロジック
       - 目的：レイキャストが敵のボックスに当たったかどうかの判定（線分 vs AABB）と、
               敵の弾が自機に当たったかの判定（球 vs AABB）。

[ ] 4. 3Dモデルの親子関係（行列の親子継承）システム
       - 目的：胴体の上に頭部を乗せ、胴体の移動・回転に合わせて頭部も自動追従させるための
               行列スタック・階層構造。

[ ] 5. サウンド再生・パーティクル管理のAPI整備
       - 目的：音素材の再生、撃破時の火花スプライトの発生をシーンから容易に呼べるようにする。


================================================================================
②【リファクタリング】の進める順（優先度順）
================================================================================
ゲームのプロトタイプが動くようになった後、コードの複雑化を防ぎ調整しやすくするために行います。

[ ] 1. マジックナンバーの定数化・一元管理
       - 目的：自機の速度、連射間隔、リロード時間、スコア配点などの調整用パラメータを
               ソースコードに直接書かず、ヘッダ定数などに集約する。

[ ] 2. JSONによるオブジェクト（配置・パラメータ）の保存・復元システム
       - 目的：ImGui上で調整した敵の出現位置やパラメータをJSONに保存し、次回起動時に自動復元。
               これにより、コードを書き換えずにステージ作成を行えるようにする。

[ ] 3. GameObject - Component システム（コンポーネント化）への移行
       - 目的：キャラクターが持つ「描画」「物理・移動」「当たり判定」「インスペクター」などの
               機能をコンポーネントに分離し、オブジェクトの多重継承やクラスの肥大化を防ぐ。
